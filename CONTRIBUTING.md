# Как внести изменения в руководство

Руководство разрабатывается по методологии Docs as Code: исходные тексты
хранятся в репозитории, любое изменение проходит через ветку, Pull Request,
автоматические проверки и ревью.

## Как предложить изменение

1. Если изменение крупное или спорное, создайте issue с описанием
   проблемы и предлагаемого правила.
2. Создайте ветку от актуальной `main`:

   ```bash
   git checkout main
   git pull
   git checkout -b feat/<краткое-описание>
   ```

   Имя ветки строится по схеме `<тип>/<краткое-описание>` латиницей
   через дефис: `feat/accessibility`, `fix/glossary-typo`.

3. Внесите изменения и проверьте их локально (см. раздел
   [«Локальная сборка»](#локальная-сборка)).
4. Сделайте коммит и отправьте ветку:

   ```bash
   git add <файлы>
   git commit -m "feat: добавить правило о метках"
   git push -u origin feat/<краткое-описание>
   ```

5. Создайте Pull Request в `main` и назначьте рецензента.

## Оформление коммитов

Сообщения коммитов оформляются по соглашению
[Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```text
<тип>: <что сделать>
```

| Тип | Когда использовать |
| --- | --- |
| `feat` | Новый раздел, правило или шаблон |
| `fix` | Исправление ошибки в тексте, ссылке или настройках, правки по ревью |
| `chore` | Настройка инструментов, CI/CD, зависимостей |
| `dev` | Служебные изменения в процессе разработки |

Требования к сообщению:

- описание пишется на русском языке, со строчной буквы, глаголом в
  инфинитиве: «добавить», «исправить», «обновить»;
- сообщение максимально короткое — не длиннее 50 символов;
- точка в конце не ставится;
- один коммит содержит одно логическое изменение.

| Неправильно | Правильно |
| --- | --- |
| `правки` | `fix: исправить ссылку на глоссарий` |
| `Добавил новый раздел про доступность и поправил меню.` | `feat: добавить раздел доступности` |

Название Pull Request оформляется так же, как сообщение коммита.

## Процесс ревью

1. После создания Pull Request автоматически запускается сценарий Lint:
   markdownlint и строгая сборка `mkdocs build --strict`. Pull Request с
   ошибками проверок не рассматривается.
2. Рецензент проверяет:
   - соответствие изменений самому руководству по стилю;
   - отсутствие противоречий с другими разделами;
   - единообразие терминов по глоссарию;
   - наличие примеров «правильно — неправильно» для новых правил;
   - добавление новой страницы в навигацию.
3. Замечания оставляются комментариями к строкам в Files changed.
4. Автор вносит правки отдельным коммитом в ту же ветку, например
   `fix: учесть замечания ревью`, и отвечает на комментарии.
5. После одобрения рецензента и успешных проверок Pull Request
   объединяется с `main`. Сценарий Deploy автоматически публикует сайт.
6. Ветка после объединения удаляется.

## Локальная сборка

Требования: Python 3.10 или выше, Node.js 18 или выше (для линтера).

1. Установите зависимости:

   ```bash
   pip install -r requirements.txt
   ```

2. Запустите локальный сервер:

   ```bash
   mkdocs serve
   ```

   Сайт откроется по адресу <http://127.0.0.1:8000> и будет обновляться
   при сохранении файлов.

3. Перед отправкой изменений выполните проверки:

   ```bash
   mkdocs build --strict
   npx markdownlint-cli2 "docs/**/*.md" "*.md"
   ```

   Обе команды должны завершиться без ошибок и предупреждений.

## Как добавить новый раздел

1. Создайте файл в каталоге `docs`. Имя пишется латиницей в нижнем
   регистре, слова разделяются дефисом: `docs/error-messages.md`.
2. Начните страницу с единственного заголовка первого уровня и короткого
   абзаца о назначении раздела.
3. Оформите правила по разделу «Правила работы с Markdown» руководства;
   для каждого правила добавьте пример.
4. Добавьте страницу в раздел `nav` файла `mkdocs.yml` в подходящее место:

   ```yaml
   nav:
     - Точечные рекомендации: tips.md
     - Сообщения об ошибках: error-messages.md
   ```

5. Если на раздел ссылаются другие страницы, задайте якорь латиницей:
   `## Заголовок {#anchor}`.
6. Проверьте сборку и линтинг, затем создайте Pull Request по процессу
   выше.
