    Оформление текста¶

    Раздел описывает, как заполняются поля задачи и как структурируется её описание.

    Обязательные поля¶

    Поле Правило
    Тип задачи Выбирается по шаблону; ошибка не заводится как Task
    Тема По правилам раздела «Стиль изложения»
    Описание Заполняется по шаблону типа задачи; пустое описание недопустимо
    Приоритет Выбирается по таблице приоритетов ниже
    Компонент Указывается модуль системы, к которому относится задача
    Метки Не более трёх меток из утверждённого списка
    Эпик Каждая Story и Task связана с эпиком

    Структура описания¶

    Описание делится на разделы с заголовками. Порядок разделов задаётся шаблоном типа задачи, общий порядок такой:

    1. Контекст — зачем нужна задача и какую проблему она решает.
    2. Что сделать — суть работы.
    3. Критерии приёмки — проверяемые условия готовности.
    4. Дополнительно — ссылки, макеты, ограничения.

    Пустые разделы шаблона удаляются, а не оставляются с пометкой «нет».

    Критерии приёмки¶

    • Критерии оформляются списком с флажками или в формате «Дано — Когда — Тогда».
    • Каждый критерий проверяется одним действием и даёт однозначный ответ «да» или «нет».
    • В критерии не используются слова «корректно», «правильно», «как обычно».
    Неправильно Правильно
    Фильтр работает корректно При выборе статуса «Оплачен» в списке остаются только оплаченные заказы
    Страница грузится быстро Страница загружается не дольше 2 секунд при 100 заказах

    Приоритеты¶

    Приоритет Когда используется
    Highest Система недоступна или теряются данные; нет обходного пути
    High Не работает ключевая функция; обходной путь неудобен
    Medium Функция работает с ограничениями; есть обходной путь
    Low Косметический дефект или улучшение без влияния на работу

    Приоритет Highest обосновывается в описании одной фразой.

    Метки и компоненты¶

    • Метки пишутся латиницей в нижнем регистре, слова разделяются дефисом: tech-debt, ux, security.
    • Новая метка добавляется в утверждённый список через Pull Request в репозиторий руководства.
    • Метки не дублируют поля: не используйте метку bug вместо типа Bug.

    Связи между задачами¶

    • Связь задаётся через поле «Связанные задачи» (Linked issues), а не упоминанием номера в тексте.
    • Используется тип связи, отражающий смысл: «блокирует», «дублирует», «относится к».
    • Перед закрытием задачи как дубликата укажите связь «дублирует» с основной задачей.

    Вложения¶

    • Снимок экрана прикладывается к ошибке, если дефект виден в интерфейсе.
    • Важная область на снимке выделяется рамкой, персональные данные закрашиваются.
    • Логи прикладываются файлом, если они длиннее 30 строк; короткий фрагмент вставляется в блок кода.
    • Имя вложения отражает содержание: cart-delete-error.png, а не image001.png.

    Комментарии¶

    • Комментарий содержит новую информацию: результат проверки, решение, вопрос.
    • Вопрос в комментарии адресуется конкретному человеку через @имя.
    • Договорённости, принятые в комментариях, переносятся в описание задачи.
